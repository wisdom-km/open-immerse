## 1. 一句话目标

只忠于用户打开的那份 PDF。第一优先级是内容精准：译文跟抽出的原文一致；公式、图、表跟原文是同一套内容。手段可以用裁图，也可以用别的，只要精准仍在。排版优先级低于精准，同时尽量做到最高。本地 GLM-OCR 只做测试；上线走 OCR API 与大模型 API。

### 1.1 优先级（2026-09-22 确认）

| 序 | 目标 | 做到什么程度 |
| --- | --- | --- |
| 1 | 内容精准 | 硬目标。译文不增、不漏、不改原文的主张。公式、图、架构图、曲线、表的内容与打开的 PDF 一致。`i` 被认成 `n`，或 `n` 被认成 `i`，都算失败 |
| 2 | 排版 | 低于内容。阅读顺序、左右对照、点击对齐、不叠字、字号可读，这些尽量做到最高。任何排版都不得改写上一条 |

公式和图的做法不锁死成唯一技术。默认是从原页裁图，因为这条已经能保住笔画。内嵌图原样取出、原页矢量原样搬过来，也可以，只要右栏结果仍与打开的 PDF 同一套内容。图内英文重画达不到精准，仍不采用。把公式认成 LaTeX 再渲染，只允许作为 §2.6 的第二层，前提是用户开启并且通过字符核对。拿不准时走 §2.6 第三层（点击看原文）。

## 2. 已确认需求

### 2.1 产品边界

| 项 | 确认 |
| --- | --- |
| 载体 | 现有 Chrome 插件，不另做桌面 App |
| 输入 | **只有 PDF**。不依赖 arXiv / LaTeX 源码 |
| 主场景 | 可下载的**发表论文纯 PDF**（数字 PDF，可复制文字） |
| 次场景 | 扫描件**少**，但 **OCR 能力保留**（无文字层时抽正文） |
| 界面 | 左栏 pdf.js 原文；右栏通读对照。点右栏块 → 左栏滚到同一区域并高亮。右栏重设计中，规格由 Loom 另出 |
| 开源 | 插件保持 MIT。不把 AGPL 的 BabelDOC 嵌进扩展包 |

### 2.2 必须极准

| 对象 | 标准 | 做法 |
| --- | --- | --- |
| 公式（含行内） | 与原文同一套内容；禁止 i/n 互认 | 默认裁原页。其他手段可以，验收标准相同。不展示未经核对的 LaTeX（见 §2.6） |
| 图、架构图、曲线图 | 与原文同一张图 | 裁得准就放进译文，配上译后题注；裁不准走 §2.6 的占位。图内英文不重绘、不翻译 |
| 表 | 第一版视觉与原文一致 | 默认整表当图，不译格子。其他手段也要整表内容不变 |
| 正文原文 | 数字 PDF 用文件里的字，不是猜的 | **优先 PDF 文字层原句** |
| 译文 | 跟抽出的原文内容精准 | 只译标题、段落、题注；公式/图/表不进模型。措辞顺滑让路给忠实 |
| 对应关系 | 读者能对上「这段译文 ↔ 原文哪一块」 | 每块 `page + bbox` |

行内公式：夹在句子里的符号也拆出去单独保住（默认是一小段裁图）。字母不送给 OCR，也不送给翻译。

公式在右栏展示原文内容。不做可复制 LaTeX，不用 KaTeX 当公式主展示。展示按 §2.6 分流：第三层是点击看原文，现有原页裁图可作缩略图。第二层例外：用户开启并且字符核对通过时，可以按 §2.6 用 KaTeX 展示该公式。

### 2.3 明确不做（第一版）

- 可复制 LaTeX（仍然不做）
- 未经核对就把公式认成 TeX 再渲染（核对通过的第二层见 §2.6）
- 图内文字译成中文并重画
- 翻译表格单元格
- 生成「长得像原论文」的中文 PDF（BabelDOC 整页回写）
- 多模态「看一整页直接出中文」
- 把译文糊进原 PDF 文字框（bbox 镜像；仓库内 #40 已否决）

### 2.4 准确度目标（能做多高做多高）

没有开源方案能对「任意 PDF + 任意句译文」签 99% 的法律保证。本项目用技术选型把 **可保证的部分推到接近 99%**，把不可保证的部分隔离并写明。

| 项 | 数字发表 PDF（主场景） | 扫描件（保留能力） |
| --- | --- | --- |
| 公式视觉 | 目标 **≥ 99%**（原页裁图，不改笔画） | 与该页扫描件一致（糊/歪属原件） |
| 图 / 架构图 | 目标 **≥ 99%**（原页裁图） | 同上 |
| 表（当图） | 目标 **≥ 99%** | 同上 |
| 正文是否抽全、抽对 | 文字层路径目标 **尽量 99%**；框划错会掉点 | OCR 上限，允许低于数字 PDF，界面提示 |
| 译文相对「抽出的原文」 | 尽量高（强模型 + 术语表 + 只译人话）；**不是公式那种像素级 99%** | 错字会传递到译文 |

内容精准是硬目标，排版是第二目标。公式、图、表用「与打开的 PDF 同一套内容」来验收，不把某一种裁图函数写成唯一合法手段。译文用强 LLM API、术语约束、数字和变量名原样保留来逼近；不在第一版用自动 BLEU 当门槛，也不为了更好看的段落去改主张。排版在不伤害内容的前提下尽量做好：阅读序、分栏不串、点击能对回左栏、右栏不叠字。

### 2.5 部署与 API（必须预留）

| 阶段 | OCR 划区 | 翻译 |
| --- | --- | --- |
| 本地测试 | 本机 GLM-OCR | 插件已配置的大模型 API，或小规模购买 API |
| 小规模试 API | 智谱 GLM-OCR 等云 API（同一 JSON） | 同上（Ark / DeepSeek / OpenAI 兼容） |
| 上线 | **只走 OCR API + LLM API** | 密钥仍在用户/产品配置的 `chrome.storage` |

架构上 **本地引擎与云 API 必须同一套块协议**。换后端只换 adapter，不改右栏渲染和裁图逻辑。  
**公式、图、表的内容永远来自用户打开的 PDF，不来自 OCR API 返回的字母。** 默认在浏览器里裁原页。换一种展示手段时，验收仍是同一套内容。这样上线接 API 也不会再出现 i/n 互认。

### 2.6 公式三层方案（2026-10-02 确认）

每个公式按三层依次尝试。上一层没把握，就交给下一层。运行时顺序是 1 → 2 → 3。开发按优先级：第一层和第三层先做（P1），第二层后做（P2）。

| 层 | 做法 | 优先级 | 可行性 | 何时采用 |
| --- | --- | --- | --- | --- |
| 第一层 | 自己识别，按原字体、原位置矢量重绘 | P1，先做 | 高 | 把握分数过阈值 |
| 第二层 | 看图大模型转成 LaTeX，再用 KaTeX 渲染 | P2，后做 | 中 | 第一层把握不足，且用户开启，且字符核对通过 |
| 第三层 | 点击看原文：占位加小缩略图，点一下左栏滚到原位置并画框高亮 | P1，先做 | 高（现有原页裁图可作缩略图） | 上面两层都没采用 |

**第一层：自己识别，矢量重绘（P1，可行性高）。** 用现有的规则算法找到公式框，再把 PDF 文件里这个框内的字符，按原字体、原位置画到右栏。字符来自文件本身，不是猜的，所以符合 §1 的「同一套内容」。前提是框要准：要认出出版社的数学字体，并修掉两类错误——公式框吞进下一行正文，以及长公式被切成好几块。每个公式还要输出一个把握分数。这个分数用练习集校准：分数说有把握时，结果要真的对。

**第二层：看图大模型（P2，可行性中）。** 第一层把握不足时，把这个公式的原页裁图交给多模态模型，转成 LaTeX，再用 KaTeX 渲染。代价是要付费、必须联网、用户要自己配 key，公式图会发给第三方。模型也可能写错，看起来却像是对的。硬约束有三条：

1. 模型输出必须和 PDF 里该框的字符核对。对不上就丢弃，降到第三层。
2. 用户可选，默认关闭。
3. 上线前先做离线实验：用 DPO 论文（arXiv 2305.18290v3）第 3–5 页的 79 个公式，测它能补回多少个第一层没把握的公式，以及核对能挡掉多少错。结果交产品方，由产品方决定是否上线。

多模态在这一层只接收该公式的原页裁图，只产出待核对的 LaTeX。看一整页直接出中文仍不做，见 §2.3。模型生成的公式旁边加一个小记号。点这个记号，左栏滚到原位置并画框高亮，用来对照核对。

**第三层：点击看原文（P1，可行性高；2026-10-02 补充）。** 右栏放一个占位，例如「公式 (4)，点击看原文」，并带一张小缩略图。点一下，左栏滚到原位置并画框高亮。现有的原页裁图可以作为这张缩略图。

**图。** 图也按这一套处理。裁得准，就直接放进译文，配上译后题注。裁不准，就走同样的占位：一句提示加上小缩略图，点一下，左栏滚到原位置并画框高亮。

**点击跳转。** 三层共用同一套点击跳转：点一下，左栏滚到原位置并画框高亮。第一层点重绘出来的公式，第二层点公式旁的小记号，第三层点占位。

**分流规则。** 第一层把握分数过阈值，就矢量重绘。否则，如果用户开了第二层并且核对通过，就用 KaTeX，并在旁边放上小记号。再否则就走第三层的占位和缩略图。

**为什么这么排。** 整套能自动分流，前提是第一层知道自己有没有把握。把握分数不准，再多层也会漏掉错的。

## 3. 从开源抄什么、不抄什么

| 项目 | 借鉴 | 不采用 |
| --- | --- | --- |
| BabelDOC / pdf2zh | 公式和图当原件搬走；只译人话；段级翻译；术语表 | 整段 AGPL 代码；字体正则当唯一公式检测；把译文塞回原框 |
| GLM-OCR / MinerU / PaddleOCR-VL | **只借划区**：label + bbox | **不借公式 LaTeX 上屏**（已实测会把 n 认成 i）。核对通过的第二层见 §2.6，不走这条 OCR LaTeX |
| 沉浸译现有 PDF 轨 | 左 pdf.js、右通读、`OI_TRANSLATE_BATCH`、实验室开关 | 文字层「恢复 LaTeX」作为公式主路径 |

核心原则：**分类用模型，展示用原文，翻译只用自然语言。** 公式第二层见 §2.6。

## 4. 总体架构

Chrome MV3 跑不动 0.9B 视觉模型。拆成三层：

```
┌──────────────────────────────────────────────────────────┐
│  Chrome 扩展（MIT，D:\open-immerse）                       │
│  左：pdf.js 原文                                           │
│  右：通读 = 译文段落 + 公式/图/表的原页裁图                  │
│  翻译：现有 OI_TRANSLATE_BATCH（LLM API）                   │
│  裁图：按 bbox 从当前页 canvas 截取（公式准度的根）          │
└────────────────────┬─────────────────────────────────────┘
                     │ 同一 JSON：blocks[]
                     │ 本地 HTTP 或 云 HTTPS（预留）
┌────────────────────▼─────────────────────────────────────┐
│  划区后端（可切换 adapter）                                 │
│  测试：本机 GLM-OCR sidecar                                │
│  试 API / 上线：GLM-OCR API（或同协议的其他 OCR API）        │
│  输出：每块 label + bbox +（仅 text/title/caption 的原文）    │
└──────────────────────────────────────────────────────────┘
```

插件 **不包含** PyTorch、vLLM、GLM-OCR 权重、BabelDOC。公式在右栏的画法按 §2.6 分流。

## 6. 块协议（本地与 API 必须一致）

```json
{
  "page": 3,
  "width": 612,
  "height": 792,
  "blocks": [
    {
      "id": "p3-b12",
      "label": "text",
      "bbox": [0.12, 0.40, 0.48, 0.55],
      "text": "We propose the Transformer..."
    },
    {
      "id": "p3-b13",
      "label": "formula",
      "bbox": [0.15, 0.56, 0.85, 0.62]
    },
    {
      "id": "p3-b14",
      "label": "figure",
      "bbox": [0.10, 0.10, 0.90, 0.38],
      "caption": "Figure 1: The Transformer architecture."
    },
    {
      "id": "p3-b15",
      "label": "table",
      "bbox": [0.12, 0.70, 0.88, 0.92]
    }
  ]
}
```

约定：

- `bbox`：归一化 `[x0,y0,x1,y1]`，与 pdf.js viewport 相乘即可裁图和高亮。
- `label`：`title` | `text` | `caption` | `formula` | `figure` | `table` | `header` | `footer`。
- **仅** `title` / `text` / `caption` 带 `text`，且数字 PDF 的 `text` **优先来自文字层与框的对齐**，不是 OCR 猜的公式字母。
- `formula` / `figure` / `table` 不带 OCR 或划区 API 返回的 `latex`。这类 API 若返回 LaTeX，适配器丢弃，不得进入右栏。只有 §2.6 第二层适配器在字符核对通过后，可以给该 `formula` 同时带上三个字段，缺一则整组丢弃、不得上屏：`latex`（核对通过的 LaTeX 字符串）、`latexSource`（来源，本方案只取 `"vlm"`）、`verified`（必须为 `true`）。`figure` 和 `table` 仍然不得带这三个字段。
- `caption` 可译；图本身只裁图。

## 7. 核心流程

```
1. 用户打开 PDF
2. 左栏立刻用 pdf.js 渲染原文（不等划区）
3. 插件把 PDF（或逐页渲染图 + 文字层）交给划区后端
     测试 → 本机 GLM-OCR
     试跑/上线 → OCR API
4. 后端只返回 blocks[]（框 + 正文原文）
5. 插件按 bbox 保住公式/图/表：默认从原页裁图；其他手段须与原页同一套内容
6. 可译块（title/text/caption）→ OI_TRANSLATE_BATCH
     术语表 + 不译数字/占位符
7. 右栏按阅读序：
     译文段落
     公式 = 按 §2.6 分流；未命中第一层、也未走通核对通过的第二层时，走第三层点击看原文
     图 = 按 §2.6：裁得准就放进译文并配译后题注，裁不准走占位
     表 = 原页裁图
8. 点击右栏块 → 左栏 scrollIntoView + 高亮同一 bbox。公式三层共用的点击跳转见 §2.6
9. 无文字层：正文改走 OCR 字，界面提示「本页可能为扫描件，正文或有识别误差」
```

数字论文主路径：**正文 = 文字层 ∩ 正文框**；**表 = 原页图**；公式和图按 §2.6。扫描件只替换「正文从哪来」，裁图逻辑不变。

## 8. 准确度如何靠技术栈撑起来

| 风险 | 对策 |
| --- | --- |
| 公式 OCR 把 n 认成 i | 公式不上 OCR 字母；只裁原图。第二层输出必须过字符核对 |
| 行内公式被当正文送去翻译 | 行内也标 `formula` 并裁图 |
| 图被重绘译坏 | 图内不译 |
| 表结构译乱 | 整表当图 |
| 正文抽错、抽漏 | 数字 PDF 用文字层；划区框与文字层求交；页眉页脚丢掉 |
| 译文不忠于原文 | 强 LLM API；按段；术语表；只译人话 |
| 上线 API 变差 | 裁图仍在浏览器；API 只划区 |

验收（建议用 Attention is All You Need 及另一份非 arXiv 的出版社 PDF）：

- 右栏公式与左栏同一位置肉眼一致，抽查无 n/i 类改字
- 架构图与原文一致，图内英文未被改
- 表为原图表，未拆格
- 右栏段落能点回左栏对应句
- 关闭本地引擎、改 OCR API 后，公式图仍然来自 PDF 裁图，不回归未经核对的「认 LaTeX」；核对通过的第二层见 §2.6

## 9. 建议落地顺序
