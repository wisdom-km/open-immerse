# 并行改同一文件

2026-10-26。多 Cloud、多 feature 一起写时记下的。功能可以互不依赖，合入时仍会因为改同一个大文件反复冲突。以后做项目、或整理成笔记，可以整篇拿走。

## 场景

两条线在功能上互不依赖，验收标准也分开写，但都会改同一个大文件。例子是 `pdf/viewer.js`：一边改翻译状态机，一边改页面内容从哪来。各自开一个 Cloud，写完再合，冲突就落在这一个文件上。解一次往往不够。main 再往前走，后合的那支还要再解一遍。时间花在对行上，合完也容易漏掉只在某一边测过的路径。

验收能分开，只说明功能边界清楚。排期时要另看两边会不会改同一段实现。

## Open Immerse 当时的例子（2026-10-26）

当天有两条都要动阅读器里的翻译流程：

- **翻译修复。** 改页面状态判定、诊断事件、重译菜单。规格是 DIAG ①–⑤，加上 RETRANSLATE-SPEC。
- **PDF 多模态优先。** 改「每一页的译文从哪来」：多模态优先，文字层兜底，再逐段核对。

两边的验收可以分开写。运行时也没有「必须先有对方的行为，自己才能测」这种依赖。冲突来自它们都在改 `pdf/viewer.js` 里那条翻译流程：状态怎么判、译文从哪取，写在同一段里。

当天的处理：

- 串行。先合底座（页面状态、诊断、重译菜单）。底座在 main 上稳定之后，再开上层（每页译文的取数管线）。
- 弹窗布局只动 `popup/`。它和上面任意一条都不抢同一个文件，可以跟其中一条并行。

## 大公司常用做法

排期时按下面五条执行。

1. **先合底座，再开上层。** 状态机、诊断、公共契约先落在 main 上，再派改行为的分支。上层从已经稳定的契约开，不和底座一起改同一段。
2. **拆边界，少改同一文件。** 状态放一个模块，取数放另一个模块。组装层只负责接线，不把判定和取数写回同一个函数。
3. **短分支、小 PR、频繁合 main。** 分支活得越久，和别人改同一文件的窗口越大。一件事合进去，再开下一件。
4. **同文件已经有人在改：后开的先同步，或约定模块所有者。** 后开的分支先接上对方已经合进 main 的改动，再写自己的。或者这块文件指定一个人收口，别人的改动从他的分支长出来。
5. **功能不冲突、文件重叠，就串行。** 晚一天开工，比两支写完再在同一个大文件里对冲突便宜。对冲突时容易把只在某一边测过的路径弄丢。

## 本仓库落地规则

- 开新 feature 之前，Forge 在任务里写明会改哪些热点文件。和已经在写的分支热点重叠，就改成串行，或者先拆模块再并行。
- 同时活跃的 feature 仍不超过 3，真机测试仍串行。活跃 PR（含审查中）的上限仍是 3。开发线仍是同一时间最多 2 个 Cloud，两条线尽量不同时改 `pdf/viewer.js` 的同一区域。出处是 [`docs/ui-phase2-plan.md`](ui-phase2-plan.md) 和 [`docs/owner-todo.md`](owner-todo.md)。
- 热点文件举例：`pdf/viewer.js`、`lib/pdf-viewer.js`、`background/service-worker.js`、`popup/` 下的文件。名单随代码拆分改，不另起一套。
- 多模态优先等翻译状态的修复合进 main 之后再开。开工时顺手把「译文从哪来」从状态判定里拆开一点，避免下一轮还是整份 `viewer.js` 对冲突。
